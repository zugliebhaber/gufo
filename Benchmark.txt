req = modellgemeldete Rate eines Requests, agg = Rate über die ganze Runde (was der Client sieht). Gesamtzuwachs c1→c32: 3,3×; pro Request fällt TG um −85 %.
Was die Kurve sagt
- Prefill ist nebenläufigkeits-invariant: req PP/s bleibt über den ganzen Bereich bei 640–672, weil der Scheduler immer nur einen Prefill-Pass gleichzeitig fährt. Der Prefill-Anteil steigt von 10,4 % auf 32,7 % allein dadurch, dass jeder Request seinen eigenen Pass zahlt.
- Aggregat skaliert, pro Request kollabiert es: agg TG/s 25,35 → 83,54 (3,3×), req TG/s 28,34 → 4,33. Jede Verdopplung bringt weniger: +46 %, +38 %, +29 %, +16 %, +8,4 %.
- Der Knee liegt bei c8. Ab c8 bringt eine Verdopplung < +30 % total, ab c16 < +17 %. Die Decode-Phase selbst läuft bei c32 noch mit 124,10 tok/s — der Unterschied zu 83,54 kommt allein aus dem serialisierten Prefill. Genau das ist die quantitative Begründung für die Prefill-Hebel (Batched Prefill / Overlap): solange 33 % der Runde One-Pass-At-A-Time-Prefill sind, bringt eine schnellere Decode-Phase kaum noch Aggregat.
- Lauf-zu-Lauf-Streuung auf diesem Host: 1–3 % (frühere Breiten-Kurve: c8/c16/c32 = 231,61 / 277,14 / 305,19).

Reproduktion:
python3 artifacts/bench_pp_tg.py --gufo build/release/gufo \
  --model-path /models/Qwen3.8-Flash-Next-GGUF/UD-Q4_K_XL/Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf \
  --model-id "Qwen3.8 Flash Next" --sessions 32 --context 1024 \
  --prefill-chunk 16384 --max-tokens 128 --prompt-repeat 6 \
  --warmup 1 --repetitions 2 --concurrency 1,2,4,8,16,32 --per-level \
  --extra-arg=--think --extra-arg=off --extra-arg=--cache-ram-bytes --extra-arg=off \
  --output artifacts/serving/pp-tg-concurrency-1-32-ctx1024.json
Hinweis: context 1024 ist nötig, weil 32 Sessions bei context 4096 den Request-State-Claim überschreiten. Wenn du die Reihe mit längeren Prompts (z. B. 1816 Token) oder mit cache on willst, sag Bescheid — dann fahre ich sie mit --sessions 16 --context 2048 bzw. geteilten Prefixen.
